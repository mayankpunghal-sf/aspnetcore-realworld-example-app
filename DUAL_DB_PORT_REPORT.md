# Dual-DB Port Report — Conduit (SQL Server + PostgreSQL)

Run: porting-agent-wizard / dual-db-port, iteration 1. Confidence score: **95** (formula and inputs in §Verification).

## 1. Summary

- **Scope ported:** the entire data-access surface — one EF Core `DbContext` (`ConduitContext`) consumed by 18 MediatR feature handlers via LINQ only. No ADO.NET, no raw SQL, no stored procedures, no Dapper, no migrations exist in the repo, so the port is concentrated in: provider selection wiring (Program.cs), the Npgsql EF Core provider, and SQL Server's case-insensitive string semantics (Appendix B6) made explicit on both engines.
- **Engines wired:** Sqlite (pre-existing default, preserved), SqlServer (pre-existing `UseSqlServer`, now correctly fed a SQL Server connection string), PostgreSql (new, `UseNpgsql` + `Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3`).
- **Switch:** `Conduit:DatabaseProvider` (`sqlite|sqlserver|postgresql`, case-insensitive) resolved once at startup into a typed `DatabaseProvider` enum; invalid values fail fast naming the key and allowed values. Zero code change / zero recompile to switch — config only.
- **Top risks:** (a) PG/SqlServer code paths were not executed in this run — no reachable engine (Docker daemon down, no SQL Server); only the InMemory integration suite (16 tests) is verified, see §10. (b) User-supplied `TagId` equality is case-sensitive on PG where SQL Server folded case (§8 flags). (c) `EnsureCreated` is used, not migrations — schema management strategy must be decided before production PG use.

## 4. Config changes

- Switch: `Conduit:DatabaseProvider` in `src/Conduit/appsettings.json` (overridable by `ASPNETCORE_Conduit_DatabaseProvider` env var, matching docker-compose.yml). Values: `sqlite` | `sqlserver` | `postgresql`. Invalid → `InvalidOperationException` naming key + allowed values. No default engine is silently assumed at runtime beyond the repo's pre-existing zero-config SQLite default.
- Connection strings (placeholders only, no secrets):
  - `ConnectionStrings:AppDb_SqlServer` = `Server=localhost,1433;Database=conduit;User Id=<SQLSERVER_USER>;Password=<SQLSERVER_PASSWORD>;TrustServerCertificate=True`
  - `ConnectionStrings:AppDb_PostgreSql` = `Host=localhost;Port=5432;Database=conduit;Username=<POSTGRESQL_USER>;Password=<POSTGRESQL_PASSWORD>;Search Path=public`
- Resolution order: engine's named string → `Conduit:ConnectionString` / `ASPNETCORE_Conduit_ConnectionString` → hard-coded SQLite default (Sqlite only). Startup fails fast if the selected engine has no usable string; placeholder markers (`<`) are rejected too.
- `Integrated Security`: not used anywhere; n/a. `MultipleActiveResultSets`: not used; n/a.

## 7. Type mapping

EF Core model → engine defaults, no overrides:

- `int` keys → int/integer identity; `string` → nvarchar/varchar(text); `byte[] Hash/Salt` → varbinary/bytea; `bool` → bit/boolean; `DateTime` → datetime2 / timestamp.
- Npgsql 10 default mapping puts `DateTime` with `Kind=Utc` into `timestamptz`; all writes are `DateTime.UtcNow` (Features/Comments/Create.cs:54-55, Features/Articles/Create.cs:88-89, Features/Articles/Edit.cs:124) and materialized values are restored to Utc by the model converter (Infrastructure/ConduitContext.cs:25-39), so the convention is already uniform. No legacy timestamp switch enabled.
- Deviations/lossy mappings: none. No `rowversion`, `hierarchyid`, `sql_variant`, TVPs, `uniqueidentifier` keys, or `datetime`-floor-dependent values exist in the model.

## 8. R9 / review flags (client-facing)

1. **`Slug` equality left exact-case** (Articles/Details.cs:30, Delete.cs:29, Edit.cs:71, Comments/Create.cs:38, Comments/List.cs:25, Comments/Delete.cs:31, Favorites/Add.cs:32, Favorites/Delete.cs:32, Articles/Create.cs:77, Edit.cs:97). Slugs are always produced lowercase by `Slug.GenerateSlug` (Infrastructure/Slug.cs:14, ASCII-only regex), so case divergence cannot arise in normal operation; lower-comparing would also be safe but was judged noise. Options: (a) keep as-is [chosen — verify slugs stay lowercase at data-import time]; (b) lower-compare like usernames; (c) citext column (schema change, `allow_schema_changes=false`).
2. **`TagId` equality left exact-case** (Articles/Create.cs:56-64, Edit.cs:163-192; Tags/List.cs:23). Tags are user-supplied strings, so PG will treat `web` and `Web` as distinct where SQL Server folded them. Options: (a) keep as-is and accept engine divergence [chosen — RealWorld spec treats tags as opaque]; (b) normalize tag casing at the API boundary; (c) citext column (schema change).
3. **PostgreSql/SqlServer paths not executed in this run** (R11): Docker daemon unavailable, no SQL Server reachable — see §10.
4. **`EnsureCreated` instead of migrations**: schema is created from the model at startup. Per-provider migration sets (dual-db-port §7) do not exist here because no migrations exist at all. Options: (a) keep EnsureCreated per engine; (b) introduce `Migrations` assembly + per-provider migration sets when schema management moves to migrations; (c) external DDL per engine.
5. **SQL Server `datetime2` (100ns) vs PG `timestamp` (1µs)**: sub-microsecond precision truncates on PG. Nothing in the code or spec asserts sub-microsecond precision; noted for awareness only.
6. **`OnDelete Restrict` on FollowedPeople FKs** is required on SQL Server (multi-path cascade cycle) and is honored identically by PG — no action, recorded because the comments cite a SqlServer-only error.
