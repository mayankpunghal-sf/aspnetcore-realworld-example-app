# Dual-DB Port Report — Conduit (RealWorld) → SQL Server + PostgreSQL

## 1. Summary
Ported `src/Conduit` (ASP.NET Core 10 + EF Core 10 RealWorld API) to run on both SQL Server and PostgreSQL behind one config switch (`Data:Provider`, values `Sqlite | SqlServer | PostgreSql`), per the `dual-db-port` contract. Zero raw SQL / ADO.NET / stored procedures existed, so the port is entirely EF-layer: provider resolved once at startup into a typed enum (R7), `UseSqlServer`/`UseNpgsql`/`UseSqlite` conditional at the composition root only, PostgreSQL package added, PG `timestamp with time zone` model fork, and B6 case-insensitivity parity via `LOWER()` on all 19 Username/Email equality lookups. SQL Server and Sqlite behavior unchanged (R1). Engines verified: none live this run (no reachable SqlServer/PG instance) — tests pass on EF InMemory; unverified paths listed in §10. Top risks: TagId case-sensitivity divergence on PG (B6/B8, R9-flagged), no per-provider migration sets (repo uses `EnsureCreated`), live-engine gap.

Confidence **92** — formula: `100 * (26/28) − 10*0 − 5*0 = 92.9 ≈ 92` (28 §9 checklist items: 26 pass, 0 fail, 2 flagged). Iterations: 1 (build fix: connection-string lookup via indexer + scoped analyzer suppressions where `ToLower()` must remain inside EF expression trees).

## 8. R9 flags (client-facing)
1. **TagId case-sensitivity (B6/B8)** — tags are stored exactly as posted (`Articles/Create.cs` does not lowercase), so on PG `Tag "ASPNET"` ≠ `"aspnet"` (SQL Server CI today), and PG unique index on `Tag.TagId` would admit `"Foo"` alongside `"foo"` (B8) — both engines diverge from SqlServer today. Options: (a) lowercase tags on write (schema-shape safe, but changes SqlServer-stored data on future writes — needs product sign-off); (b) `citext` on Tag.TagId (requires extension + collation decision); (c) ICU nondeterministic CI collation on the column (requires pre-created collation since `EnsureCreated` cannot create collations). Not picked silently (R2/R9) — flagged.
2. **Sqlite default when switch missing** — §2 contract says fail-fast/no default engine; empty → `Sqlite` preserves the documented `make run-local` / managed-server flows (R1). Options: strict fail-fast (breaks existing dev workflow) or a `Data:Provider` default in appsettings.json. Deviation is explicit and single-purpose.
3. **Slug equality CS on PG (B6)** — exact-match lookups are CS on PG; slugs are lowercase by construction (`Slug.GenerateSlug` → `ToLowerInvariant`) so collisions require hand-crafted requests. Options: same three as #1 if strict CI is required.
4. **No per-provider migration sets** — repo has zero migrations (`EnsureCreated` both engines generate per-provider DDL at startup). §7 two-migration-set rule is future work the moment real migrations are introduced.
5. **launchSettings.json stale keys** (`DB_TYPE`, `DB_CONNECTION_STRING`) — dead config, left untouched (R10); delete or migrate to `Data__Provider` when the dev profile is next touched.
6. **Analyzer suppressions** — CA1304/CA1311/CA1862 disabled file-scoped in the 11 touched feature files with justification comments: `string.ToLower()` must stay inside EF expression trees to translate to `LOWER()`; `string.Equals(StringComparison)` is not translatable to SQL.
