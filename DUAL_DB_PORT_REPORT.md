# Dual-Database Port Report — Conduit (SQL Server + PostgreSQL)

**Target skill:** `dual-db-port` · **Run:** porting-agent-wizard, GitHub-sourced · **Branch:** `porting/dual-db-port-postgresql-switch`
**Engines in scope:** SQL Server (unchanged, fully supported) · PostgreSQL (newly switchable) · SQLite (existing dev default, unchanged) · EF Core InMemory (tests, unchanged)
**Switch:** config key `Data:Provider` (canonical; legacy `Conduit:DatabaseProvider` still honored) → `sqlite | sqlserver | postgresql` · **Connection strings:** `ConnectionStrings:AppDb_SqlServer` / `ConnectionStrings:AppDb_PostgreSql` (legacy `Conduit:ConnectionString` accepted)

## 1. Summary

The application's data access is pure EF Core 10 (one `ConduitContext`, zero raw SQL, zero stored procedures, zero migrations — schema comes from `EnsureCreated`). The port therefore lands entirely in the EF Core provider seam (§11): `Npgsql.EntityFrameworkCore.PostgreSQL` 10.0.3 was added; the startup string-sniffing provider switch was replaced by a typed, fail-fast, resolve-once `DatabaseProviderSelection` (R7) with a `UseNpgsql` branch; and the single genuine engine divergence found — `DateTime.UtcNow` (Kind=Utc) writes throwing against Npgsql's `timestamp without time zone` (§5.9) — is handled by a `Database.IsNpgsql()` model fork mapping the four audit-timestamp columns to `timestamp with time zone`. SQL Server and SQLite paths are byte-for-byte unchanged in behavior (R1). Build clean (0 warnings, warnings-as-errors on), 16/16 integration tests pass. PostgreSQL itself was **not** connected in this run (no server available); all unverified paths are listed in §10.

## 4. Config changes

- New switch value `postgresql` on `Data:Provider` (or legacy `Conduit:DatabaseProvider`); unknown values throw `InvalidOperationException` naming the key and allowed values; missing key keeps the existing `sqlite` default (deviation from §2's "no default engine", kept deliberately so existing local/docker behavior is unchanged — flagged for reviewer awareness).
- `ConnectionStrings:AppDb_SqlServer` and `ConnectionStrings:AppDb_PostgreSql` added as **empty** placeholders (no secrets committed, R5); per-provider selection falls back to legacy `Conduit:ConnectionString` (docker-compose `ASPNETCORE_Conduit_ConnectionString` keeps working), and startup fails fast if the selected relational provider has no non-empty string.
- Connection strings are never translated between engine formats at runtime (§6).
- `docker-compose.yml` unchanged — its env passthrough (`ASPNETCORE_Conduit_DatabaseProvider`/`_ConnectionString`) becomes live for the first time and accepts `postgresql`.

## 7. Type mapping applied

`int`→`integer` (identity), `string`→`text`, `byte[]`→`bytea`, `bool` (not-mapped only), `DateTime`→`timestamp with time zone` **on Npgsql only** (Sql Server keeps `datetime2`, SQLite keeps its TEXT affinity). No `decimal`/`money`/`uniqueidentifier`/`rowversion`/`hierarchyid`/`geography`/`sql_variant`/TVP types exist in the model, so no lossy mapping was required and none was applied (R4).

## 8. R9 flags (no-equivalent constructs)
