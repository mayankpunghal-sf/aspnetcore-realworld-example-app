# DUAL_DB_PORT_REPORT.md — Conduit (RealWorld) dual-engine data access port

## 1. Summary

Scope ported: `src/Conduit` (the sole data-access project; EF Core 10) plus its composition root, configuration, and test lock files. The application now selects its engine exactly once at startup from the `Data:Provider` configuration key (`SqlServer` | `PostgreSql`), with both named connection strings (`AppDb_SqlServer`, `AppDb_PostgreSql`) configured side by side. SQL Server behavior is unchanged (R1): same provider, same model defaults, same queries. PostgreSQL is reached by switching one config value + connection string, zero code change. The codebase contained zero raw SQL, zero ADO.NET, and zero stored procedures, so the port is concentrated in the provider switch, packages, and per-engine physical model mapping. Top risks: (1) PostgreSQL requires a `conduit_ci` ICU collation to exist before `EnsureCreated` (see §8/§11); (2) engines were not live-verified in this environment (§10).

Engines verified: build + 16/16 integration tests (EF InMemory). SQL Server / PostgreSQL live connections: not available here — see §10 for the unverified-path list.

## 4. Config changes

- Switch: `Data:Provider` = `SqlServer` | `PostgreSql`. Missing/empty/unknown → `InvalidOperationException` at startup naming the key and allowed values. No default engine (§2). Resolved once into `DatabaseProvider` via `IDatabaseProviderAccessor` (R7).
- Named connection strings side by side (never translated at runtime):
  - `AppDb_SqlServer`: `Server=<host>,1433;Database=<database>;User Id=<user>;Password=<password>;Encrypt=True;TrustServerCertificate=True;` (placeholder — SqlClient 4+ defaults `Encrypt=True`)
  - `AppDb_PostgreSql`: `Host=<host>;Port=5432;Database=<database>;Username=<user>;Password=<password>;SSL Mode=Require;Trust Server Certificate=true;Search Path=public;` (placeholder — `Search Path` pinned per §6 pooling note)
- Startup validation: selected provider's named connection string must exist and be non-empty or startup fails fast.
- `docker-compose.yml` passes `Data__Provider`, `ConnectionStrings__AppDb_SqlServer`, `ConnectionStrings__AppDb_PostgreSql` through; `launchSettings.json` dev profile configures SQL Server (LocalDB).
- No credentials committed (R5): all strings are `<placeholder>` templates; `appsettings.json` contains none.

The EF provider conditional at the composition root is the dialect seam for this stack (§11).

## 6. SQL changes

None required: there is no hand-written SQL (no `FromSqlRaw`/`ExecuteSql*`/readers — grep-verified). All SQL is generated by EF Core from LINQ and fully parameterized on both engines (R6 satisfied structurally). Pagination (`Skip/Take` after `OrderBy`) translates to `OFFSET/FETCH` (SQL Server) / `LIMIT/OFFSET` (PG) — both engine-native, no fork needed.

## 8. R9 flags / open items for review

1. **`conduit_ci` collation prerequisite (PG).** Why: EF Core / `EnsureCreated` cannot create database collation objects, yet the CI-equality parity fork references one. Options: (a) runbook DDL before first run (recommended): `CREATE COLLATION conduit_ci (provider = icu, locale = 'und-u-ks-level2', deterministic = false);` — parity with SQL Server CI for equality + unique enforcement; note nondeterministic collations do not support `LIKE`/pattern operators (none used). (b) `citext` extension for Username/Email — extension dependency, per-column type change. (c) accept case-sensitive matching on PG (behavior divergence vs SQL Server) — smallest setup, largest semantic gap.
2. **Live-engine verification gap.** No SQL Server or PostgreSQL instance was reachable in the porting environment; all verification is build + InMemory tests (R11). Listed explicitly in §10.
3. **No migration sets.** Repo has zero migrations; schema comes from `EnsureCreated()`. Logical shape frozen (R3). Recommended before production PG rollout: introduce per-provider migration sets (§7) so model changes generate both DDLs; `EnsureCreated` cannot evolve a schema.
4. **Local-dev SQLite default removed.** The `sqlite` engine was removed from the host wiring: the contract switch accepts exactly `SqlServer` | `PostgreSql` with no default engine (§2), and sqlite is outside the port's scope. Local runs now require `Data__Provider` + a connection string (launchSettings provides SQL Server/LocalDB values).

## 11. Rollout prerequisites (PostgreSQL 16)

- Create collation before first `EnsureCreated`: `CREATE COLLATION conduit_ci (provider = icu, locale = 'und-u-ks-level2', deterministic = false);` (ICU support requires PG16 ✓).
- Extensions: none required (no pgcrypto/citext/postgis/tablefunc usage).
- Auth model: user/password (SCRAM) via `AppDb_PostgreSql` placeholder; no integrated auth on PG — infra prerequisite if SQL Server used Windows auth.
- `search_path`: pinned via `Search Path=public` in the connection string (pooled sessions reset session state).
- Pooling: `Maximum/Minimum Pool Size` tunable on the PG connection string; SQL Server `Max/Min Pool Size` unchanged.
- Retry-on-`40001`: not required today (only default `ReadCommitted` is used; no RR/SERIALIZABLE paths).
- Sequence re-sync: n/a under `EnsureCreated` (identity handled by provider); becomes a runbook item if migration sets are introduced (§8.3).
- Engine switch smoke test: set `Data__Provider=PostgreSql` + `ConnectionStrings__AppDb_PostgreSql=...` → start → `EnsureCreated` builds schema → hit `/api/tags` (read) and user/article flows (write).
- MARS: not used anywhere (§5.8 N/A). Migrations: recommended per §8.3.
